# ביצועים

המסמך מכסה את סעיף 6 באפיון: אילו פעולות נבחנו, איך, אילו אינדקסים נוספו ולמה, ואיפה צוואר הבקבוק.

## איך נמנעת טעינה של כל הנתונים לזיכרון

- `RequestQueryService` בונה `IQueryable` אחד: הסינון, החיפוש, המיון וה-`Skip/Take` מתורגמים ל-SQL (`WHERE … ORDER BY … OFFSET/FETCH`) ורצים ב-SQL Server.
- ההקרנה ל-DTO (`RequestMapping.ToRow`) נעשית בתוך ה-`Select`, כך שנשלפות רק העמודות הנדרשות, ורק שורות העמוד המבוקש (עד 100).
- הספירה (`TotalCount`) היא `COUNT(*)` בבסיס הנתונים, לא `Count()` על רשימה.
- ה-Aggregations הם `GROUP BY` בבסיס הנתונים, ומוחזרות מהם 4 + 3 שורות בלבד.
- `AsNoTracking` בכל השליפות, כדי שלא נשמר מצב ב-Change Tracker.

## אינדקסים

| אינדקס | תרחיש | למה |
|---|---|---|
| `IX_Requests_CreatedAt` | תצוגת ברירת המחדל (החדשות קודם), סינון לפי טווח תאריכים | Seek על הטווח, וקריאה בסדר האינדקס בלי אופרטור SORT |
| `IX_Requests_Status_CreatedAt` | סינון לפי סטטוס + מיון ברירת מחדל; `GROUP BY Status` | עמודה מובילה לסינון (Seek), ו-CreatedAt כעמודה שנייה נותן את סדר המיון "בחינם" |
| `IX_Requests_Priority_CreatedAt` | סינון לפי עדיפות; `GROUP BY Priority` | כמו הקודם |
| `IX_Requests_AssignedTo_CreatedAt` | "הפניות שלי" + טווח תאריכים | שוויון על AssignedTo וטווח על CreatedAt באותו Seek |
| `IX_Requests_OrganizationName` | סינון לפי ארגון ("מתחיל ב…"), מיון לפי ארגון | `LIKE 'x%'` ניתן לביצוע כ-Seek |
| `IX_RequestStatusHistory_RequestId_ChangedAt` | היסטוריה של פנייה | Seek לפי פנייה, כבר ממוין לפי זמן |

לא נוספו אינדקסים מכסים (`INCLUDE` של כל העמודות). בעמוד של 20 שורות, Key Lookup לכל שורה זול. אינדקס מכסה היה מכפיל את נפח האחסון ואת עלות הכתיבה, בלי תועלת ממשית.

### תרחישי החיפוש והסינון המרכזיים

אותו מידע, מסודר לפי מה שהמשתמש עושה. העמודה "מה קורה" מתארת את התוכנית הצפויה לפי התכנון, ומאומתת מול ה-Execution Plan בפרק "תוצאות".

| תרחיש | אינדקס | מה קורה |
|---|---|---|
| פתיחת המסך (החדשות קודם, בלי סינון) | `IX_Requests_CreatedAt` | נקראות 20 השורות הראשונות לפי סדר האינדקס, בלי מיון |
| סינון לפי סטטוס | `IX_Requests_Status_CreatedAt` | Seek לסטטוס המבוקש, והשורות כבר ממוינות לפי תאריך |
| סינון לפי עדיפות | `IX_Requests_Priority_CreatedAt` | כמו בסטטוס |
| מטפל + טווח תאריכים ("הפניות שלי") | `IX_Requests_AssignedTo_CreatedAt` | Seek אחד שמכסה גם את המטפל וגם את הטווח |
| טווח תאריכים בלבד | `IX_Requests_CreatedAt` | נקרא רק הטווח המבוקש |
| סינון לפי ארגון ("מתחיל ב…") | `IX_Requests_OrganizationName` | Seek לארגונים המתאימים, ומיון של השורות שנמצאו בלבד |
| כמה מסננים יחד | האינדקס המצמצם ביותר | ראו "סינון משולב" למטה |
| חיפוש חופשי (`search=Refund`) | **אין** | `LIKE '%x%'` לא יכול להשתמש באינדקס רגיל. בשילוב עם מסנן אחר, החיפוש רץ רק על השורות שהמסנן השאיר. שיפור מוצע: Full-Text Index (ראו "צווארי בקבוק") |
| מיון לפי כותרת, תאריך עדכון או עדיפות | **אין, בכוונה** | השורות המסוננות ממוינות ונשמרות רק 20 הראשונות (Top-N Sort). ב-100,000 שורות זה מהיר, ואינדקס לכל אפשרות מיון היה מאט כל עדכון ומגדיל את נפח האחסון |

### סינון משולב

לא נבנה אינדקס לכל צירוף של מסננים: יש עשרות צירופים אפשריים, וכל אינדקס נוסף מאט את הכתיבה ותופס מקום. בסינון משולב, SQL Server בוחר אינדקס אחד, זה שמצמצם הכי הרבה שורות (למשל לפי מטפל: כ-2% מהטבלה). הוא קורא דרכו רק את השורות המתאימות, ובודק את שאר התנאים (סטטוס, עדיפות, חיפוש) רק עליהן. כל מסנן שמוסיפים מקטין את התוצאה ולא מגדיל את העבודה, ולכן מספיק אינדקס אחד טוב לכל עמודת סינון מרכזית.

## שיטת המדידה

נבחנו שתי הפעולות המרכזיות של ה-API:
- **`GET /api/requests`**: רשימה עם סינון, חיפוש, מיון ודפדוף. כל קריאה מריצה שתי שאילתות: `COUNT` ושליפת עמוד.
- **`GET /api/requests/summary`**: ה-Aggregations.

הסקריפט [perf/measure.ps1](perf/measure.ps1) מריץ את השאילתות כפי ש-EF Core שולח אותן (עם פרמטרים), על 100,000 הרשומות מה-Seed. לכל שאילתה הוא אוסף:

- **logical reads** (`SET STATISTICS IO`): מספר דפי הנתונים (8KB) ש-SQL Server קרא. זה המדד העיקרי, כי הוא יציב ולא תלוי בעומס על המחשב.
- **Actual Execution Plan** (`SET STATISTICS XML`): אילו אופרטורים ואינדקסים נבחרו בפועל, וכמה שורות עברו בכל אופרטור.
- **זמן ממוצע** של 20 הרצות, אחרי חימום (הנתונים כבר בזיכרון, כמו במערכת שרצה). הזמנים מקורבים ומשתנים בכמה אחוזים בין הרצות.

להרצה: `powershell -ExecutionPolicy Bypass -File docs\perf\measure.ps1`. לצפייה גרפית ב-Execution Plan ב-SSMS יש את [perf/measure.sql](perf/measure.sql) (מריצים עם Ctrl+M).

סביבה: SQL Server 2022 Express, מחשב נייד (Intel i5-7300U), 100,000 פניות.

### מה התוצאות מראות

- **אין טעינה מלאה לפני דפדוף וסינון.** בכל התוכניות, `Top` עוצר אחרי 20 שורות, והסינון מתבצע ב-Seek בתוך האינדקס. לשרת האפליקציה מגיעות 20 שורות בלבד.
- **האינדקסים עובדים כמתוכנן.** בכל תרחישי הסינון המרכזיים (Q0, Q1, Q3) נבחר האינדקס שתוכנן לתרחיש, בלי אופרטור Sort, בכ-71 קריאות ובפחות ממילישנייה.
- **ההשוואה Q1 מול Q1′:** בלי האינדקס, SQL Server קורא את כל הטבלה (1,997 דפים) וממיין. עם האינדקס הוא קורא **פי 28 פחות** דפים, ומהיר **פי 60–80**.
- **Summary:** ‏SQL Server בחר לסרוק את האינדקס הצר (Status או Priority, כ-750 דפים) במקום את הטבלה המלאה (1,997 דפים). זה עדיין סריקה של 100,000 שורות בכל קריאה, ולכן התוצאה נשמרת ב-Cache.

## צווארי בקבוק והצעות שיפור

הסדר הוא לפי ההשפעה שנמדדה.

### 1. חיפוש טקסט חופשי: צוואר הבקבוק העיקרי

**מה נמדד:** קריאה אחת עם `search` עולה כ-0.4 שניות (בעיקר בגלל ה-`COUNT`). במונח נדיר היא עולה עד כ-1 שנייה. כל שאר הפעולות לוקחות כמה מילישניות.

**למה:**
- `LIKE '%x%'` לא יכול להשתמש באינדקס, ולכן הספירה סורקת את כל 100,000 השורות, ובכל שורה משווה שתי מחרוזות. העלות היא בעיקר CPU: רק 1,997 דפים, אבל 400ms.
- בשליפת העמוד, SQL Server **לא יכול להעריך** כמה שורות יתאימו לחיפוש באמצע מחרוזת. לכן הוא בוחר לעבור על `IX_Requests_CreatedAt` לפי הסדר ולבדוק כל שורה, בתקווה למצוא 20 התאמות מהר. במונח נפוץ ("Refund") זה מצוין: הוא עובר רק על 232 שורות. במונח נדיר הוא עובר על **כל** 100,000 השורות, עם Key Lookup לכל אחת: 306,983 קריאות, פי 150 מסריקה ישירה של הטבלה.
- בדקנו אם הבעיה היא תוכנית ישנה שנשמרה (Parameter Sniffing): הרצה עם `OPTION (RECOMPILE)` בחרה **אותה תוכנית בדיוק**. כלומר הבעיה היא חוסר היכולת להעריך `LIKE '%x%'`, ולא תוכנית שנשמרה.
- **בשילוב עם מסנן אחר** (למשל מטפל), החיפוש רץ רק על השורות שהמסנן השאיר: 558 קריאות, ~1.5ms.

**הצעת שיפור:** Full-Text Index על Title ו-OrganizationName, וחיפוש עם `CONTAINS` (לפי מילים או קידומת מילה). האינדקס הזה בנוי בדיוק לחיפוש מילים בתוך טקסט, ונותן לבסיס הנתונים גם הערכה נכונה של מספר התוצאות. השינוי בקוד מצומצם לשורת החיפוש ב-`RequestQueryBuilder` ולמיגרציה. הוא לא מומש כי Full-Text דורש רכיב שלא קיים בכל התקנה של SQL Server (למשל באימג' הבסיסי של Docker), וכי ב-100,000 רשומות 0.4 שניות עדיין סביר. חלופות זולות יותר: ספירה מקורבת או מוגבלת בחיפוש (למשל "1,000+"), או חיפוש "מתחיל ב…" בלבד, שמשתמש באינדקס.

### 2. דפדוף עמוק (OFFSET גדול)

**מה נמדד:** עמוד 1000 קורא 61,413 דפים, **יותר מסריקה של כל הטבלה** (1,997). הסיבה: SQL Server מביא את כל העמודות (Key Lookup) עבור כל 20,000 השורות שמדלגים עליהן, ולא רק עבור 20 השורות שמוחזרות.

**הצעת שיפור, נמדדה (Q2′):** ‏Deferred Join. קודם מוצאים את 20 המזהים של העמוד באינדקס הצר בלבד, ורק אחר כך שולפים את השורות המלאות עבור 20 המזהים האלה. התוצאה: **214 קריאות במקום 61,413, ו-~4ms במקום ~40ms**. ב-EF Core זה שתי שאילתות קצרות: מזהים, ואז `WHERE Id IN (...)`. לא מומש כי משתמשים כמעט לא מגיעים לעמוד 1000, ו-40ms עדיין סביר. לגלילה רציפה, החלופה הטובה ביותר היא Keyset Pagination (`WHERE (CreatedAt, Id) < (@last...)`).

### 3. מיון לפי שדה בלי אינדקס

**מה נמדד:** מיון לפי כותרת: ~330ms. סריקה של כל הטבלה ומיון.

**ההחלטה:** במכוון אין אינדקס לכל אפשרות מיון (ראו "תרחישי החיפוש והסינון המרכזיים"). אם בשימוש אמיתי יתברר שמיון לפי כותרת או תאריך עדכון נפוץ, אפשר להוסיף `IX_Requests_Title` או `IX_Requests_UpdatedAt`, והם יורידו את השאילתה לכ-71 קריאות כמו Q0. המחיר: אינדקס נוסף שמתעדכן בכל כתיבה.

### 4. `COUNT(*)` בכל קריאת רשימה

הספירה זולה בסינון רגיל (~5ms ב-Q1), אבל היא החלק היקר בחיפוש (~400ms). **שיפור:** לא לספור כשמדפדפים קדימה (להחזיר רק "יש עמוד הבא"), או לשמור את הספירה ב-Cache לזמן קצר לכל שילוב מסננים.

### 5. Summary

~16ms לכל אחת משתי הספירות, וכל משתמש שפותח את המסך מבקש אותן. לכן הן נשמרות ב-Cache ומתנקות בכל שינוי סטטוס (ראו README). בהיקפים גדולים בהרבה אפשר להחליף אותן ב-Indexed View עם `COUNT_BIG` לפי סטטוס, ש-SQL Server מעדכן בכל כתיבה, וכך הקריאה עצמה כמעט בחינם.
